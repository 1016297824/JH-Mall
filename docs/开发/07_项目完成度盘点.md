## 二、必须知道的链路断点（按优先级）

| # | 断点 | 证据 | 影响 |
| :-: | --- | --- | --- |
| 1 | **下单依赖不存在的端点** | `RemoteUserService:121` 声明 `/inner/user/addresses/validate`（其 Javadoc 自述提供方**尚未提供**）；`mall-user` 的 `RemoteUserInnerController` 实无此端点；`OrderServiceImpl:114` **无条件**调用且 Feign 无 fallback | **下单接口运行期必然失败** |
| 2 | **无发货 / 揽收入口** | `OrderStateMachine:199,214` 定义 `SELLER_DELIVER` / `LOGISTICS_PICK`，但全仓**仅状态机与单测命中**；`MallOrderMapper.updateLogistics:143` 无调用方；mall-admin 是纯 CRUD | **支付后订单永久停在"已支付"** → 无法完成 → 积分/成长值不发、自动收货扫不到、退货退款无法申请 |
| 3 | **售后 `afterSaleNo` 契约不匹配** | mall-order 传**主键 id**（`AfterSaleServiceImpl:235`）→ mall-payment 当 `after_sale_no` 落库（`RefundServiceImpl:126`）→ 回调带回 → mall-order 按**业务单号**查库（`MallAfterSaleMapper:28`）→ **必然查不到** | 售后单**永久停 REFUNDING**；退货退款不回补库存（`restock` 的幂等键因此跑不到） |
| 4 | **商品变更 → 搜索同步完全断路** | `SearchSyncProducer.syncProduct:41` **全仓零调用方**；`mall:search:sync` 通道**有消费者无生产者**；`SearchSyncScheduleTask` 仅由 ruoyi-job 调用，而 `sys_job` 种子数据**未注册**该任务；`IndexServiceImpl:346` 吞掉全部异常使 Outbox 兜底失效；`:150` 的 1 小时去重键会误杀正常二次变更 | 改价/上下架后 **ES 索引不更新**，且无自动恢复手段 |
| 5 | **订单完成事件不带 `points` / `orderAmount`** | 生产端 payload 只有 `orderNo`/`userId`（`OrderServiceImpl:434`、`OrderTimeoutFallbackTask:120`）；消费端两个 `if` 要求这两个字段（`UserOrderCompletedConsumer:60,79`） | **积分与成长值永不发放**，且静默 no-op 无告警 |
| 6 | **支付渠道全 Mock** | `PaymentChannelFactory:38-44`：`mock-enabled=false` 直接抛错，无其他路由；微信/支付宝适配器类**不存在**；验签是 `sign == "MOCK_SIGN"` 常量比对（`MockPayAdapter:203`）；账单查询恒 `UNKNOWN` | 无法真实收款；**知道常量即可伪造支付成功回调** |
| 7 | **内部接口签名机制未装配** | `InnerSignatureFilter` / 拦截器带 `@Component` 但在 `com.mall.api` 包下，而 7 个模块 `scanBasePackages` 均不含它，`mall-api` 也无 `AutoConfiguration.imports` | 跨服务 `/inner/**`（含密码哈希、库存写、券写）**直连端口无防护** |
| 8 | **退款回调后订单不推进** | `AfterSaleServiceImpl.refundCallback:192-208` 只改售后单，未触发 `REFUND_SUCCESS`；该事件仅在状态机与单测出现 | 订单永久 `REFUNDING`，永不 `REFUNDED` |
| 9 | **售后审核无入口** | `AfterSaleService.approve/reject:44,52` 有完整实现，但**无 Controller、无 MQ、管理端也不经 Feign**（mall-admin 零 `@FeignClient`） | 审核 → 退款 → 回补 链路代码内不可达 |

## 三、可执行任务清单

> 每项给出**验收标准**（可客观判定）与主要落点。P0 全部完成后，C 端后端主链路才真正跑得通。

### P0 — 打通后端主链路

| # | 任务 | 验收标准 | 主要落点 |
| :-: | --- | --- | --- |

| P0-4 | 搜索同步接上触发点 | 改价/上下架后 N 秒内 ES 可搜到新值；ES 不可用时 Outbox 有记录且补偿可投递；同一商品连续两次变更**不丢**第二次 | 商品写路径调用 `SearchSyncProducer.syncProduct`；`IndexServiceImpl:346` 不再吞异常；`:150` 去重键语义调整；`sys_job` 注册补偿任务（或改 `@Scheduled`） |
| P0-5 | 退款回调推进订单状态 | 售后完成后订单进入 `REFUNDED`，`pre_refund_status` 回退逻辑可触发 | `AfterSaleServiceImpl.refundCallback` 补 `REFUND_SUCCESS` 状态流转 |

## 四、已验证可靠、不要重复劳动的部分

这几块经审计确认是**真实实现**（非 Mock、非占位），修复其他问题时请以其为基准：

| 能力 | 证据 |
| --- | --- |
| **库存预扣 / 释放 / 回补幂等** | `StockServiceImpl:52-74 / 78-136 / 170-202`：乐观锁 + Redis 预扣键 + `bizNo` 幂等 + 失败释放幂等键 + 影响行数校验 |
| **券锁定 / 核销 / 释放** | `CouponStateMachine:155-191` + `CouponClaimServiceImpl:109-198`（CAS 决定是否回补） |
| **Outbox 可靠性**（order / payment / marketing） | 同事务落库、`selectPending` 按 `scheduled_time` 过滤、失败退避重试并置 `FAILED` |
| **MQ 消费可靠性**（6 个消费者） | 失败先 `dedupGuard.release` 再抛；`OrderTimeoutConsumer` 的事务边界落在 `onMessage`；非法数据置 `FAILED` 防毒丸 |
| **ES 搜索本体** | `SearchServiceImpl` 走真实 `ElasticsearchOperations`；`IndexServiceImpl` 含真实 ik mapping、别名切换、回滚 |
| **认证闭环** | `CaptchaController` 6 端点全真实（注册/登录/重置密码/换绑手机/注销）；`MallAuthFilter` 校验签名/过期/黑名单/token_version；refreshToken 一次性轮换 |
| **管理端** | 20 视图 + 20 api 模块真实对接，`build:prod` 通过 |
| **测试基线** | mall 侧 636 例 0 失败（2026-10-03）；前端 31 单测 + e2e 配置齐备 |
